# Professional Diagramming & Architecture Guidelines

This document outlines the architectural standards, visual rules, and information hierarchy used by our diagram generation and layout engine. It is inspired by industry-leading systems such as **Eraser.io**, **IcePanel (C4 Model)**, **DrawSQL**, and **AWS Architecture Framework**.

---

## 1. The C4 Model Architectural Hierarchy

When modeling software systems, diagrams must follow clear abstraction levels:

### Level 1: System Context
- **Focus**: High-level view showing human actors (users, administrators) and external systems interacting with the central system boundary.
- **Rules**:
  - Keep the core system as a focal point.
  - Show external services (e.g., Stripe, SendGrid, Auth0) as distinct external nodes.
  - Connections must specify protocol and high-level intent (e.g., `HTTPS / OAuth2`, `Webhooks`).

### Level 2: Container (Applications & Data Stores)
- **Focus**: High-level technical architecture. A "container" is an independently deployable/runnable unit (e.g., Single Page App, API Backend, Database, Message Broker, Cache).
- **Rules**:
  - Every container MUST specify its concrete technology stack in `metadata.tech` (e.g., `Next.js 14`, `Go / Gin`, `PostgreSQL 16`, `Redis 7`).
  - Assign each container to a distinct architectural layer (e.g., `Client`, `Edge/Gateway`, `Microservice`, `Data Store`, `Message Queue`).
  - Edges must state communication protocols (e.g., `HTTPS / JSON`, `gRPC / Protobuf`, `TCP / SQL`, `WSS`).

### Level 3: Component
- **Focus**: Internal structure of a single container (e.g., controllers, services, repositories inside an API container).
- **Rules**:
  - Show interactions between modules.
  - Maintain single direction of dependency (Controller -> Service -> Repository).

## 2. Topological Layering & Graph Flow

A professional diagram should read naturally with minimal edge crossings and clear flow direction.

### Standard Flow Direction:
- **Left-to-Right (`LR`)**: Preferred for:
  - System Architecture Diagrams
  - Data Processing Pipelines & Event Streams
  - Database Entity-Relationship Diagrams (ERDs)
  - Network & Cloud Infrastructure
- **Top-to-Bottom (`TB`)**: Preferred for:
  - Flowcharts & Decision Trees
  - BPMN Workflows
  - Hierarchical Organization Charts
  - Step-by-Step User Journeys

### Tiered Ranking Rules (Left-to-Right layout):
1. **Tier 0 (Entrypoints)**: Actors, Browser, Mobile App, CLI (`type: "user" | "actor"`)
2. **Tier 1 (Edge & Gateway)**: CDN, Cloudflare, API Gateway, Reverse Proxy, Ingress (`type: "frontend" | "api" | "gateway"`)
3. **Tier 2 (Core Application Services)**: Business logic, microservices, auth server, worker nodes (`type: "backend" | "service" | "task"`)
4. **Tier 3 (Asynchronous & Event Bus)**: Kafka, RabbitMQ, SQS, Redis Pub/Sub (`type: "queue"`)
5. **Tier 4 (Persistence & Storage)**: PostgreSQL, MongoDB, Redis Cache, S3 Object Store (`type: "database" | "cache"`)
6. **Tier 5 (Third-Party Integrations)**: Stripe, Twilio, OpenAI API, AWS SES (`type: "external"`)

> [!IMPORTANT]
> **No Inverted Dependencies**: Databases or external APIs must never initiate direct unsolicited connections backwards to client apps. The flow must strictly follow real-world network protocols.

## 3. Node Metadata & Semantic Standards

Every node generated by the system should include rich structured metadata:

```json
{
  "id": "payment_service",
  "label": "Payment Service",
  "type": "backend",
  "description": "Processes credit card checkouts and webhook events",
  "metadata": {
    "tech": "Node.js / Express",
    "layer": "MICROSERVICE",
    "badge": "PCI-DSS v4",
    "status": "active",
    "category": "backend"
  }
}
```

### Supported Metadata Fields:
- `tech`: String describing the specific framework or technology (e.g., `PostgreSQL 16`, `FastAPI`, `Next.js`, `Apache Kafka`).
- `layer`: Logical layer badge displayed at the top of the node card (e.g., `CLIENT`, `GATEWAY`, `CORE SERVICE`, `STORAGE`, `BROKER`, `SECURITY`).
- `badge`: Short descriptive pill (e.g., `Primary`, `Replica`, `v2 API`, `Serverless`).
- `status`: Node health indicator (`active`, `healthy`, `syncing`).

## 4. Connector & Edge Semantics

Connectors must communicate **how** components interact, not just that a line exists.

### Edge Protocols:
- **Web / Mobile -> API Gateway**: `HTTPS / TLS 1.3 (REST / JSON)`
- **Real-Time Client -> Server**: `WSS (WebSocket)`
- **Inter-Service Communication**: `gRPC / HTTP/2` or `Internal REST`
- **Service -> Message Queue**: `pub/sub (Kafka Topic)` or `AMQP`
- **Service -> Database**: `TCP / SQL (Pool)` or `Read/Write`
- **Service -> Cache**: `Cache Lookup (Key/Value)`
- **Service -> External API**: `HTTPS / REST (Bearer Token)`

### Edge Visual Styles:
- **Solid (`type: "default" | "smoothstep"`)**: Synchronous, blocking request/response calls.
- **Dashed (`style: { strokeDasharray: "5,5" }`)**: Asynchronous, decoupled event publishing or batch jobs.
- **Animated (`animated: true`)**: Active streaming pipelines, message bus traffic, real-time WebSockets.

## 5. Entity-Relationship (ERD) Standards

1. **Table Names**: Lowercase snake_case (e.g., `users`, `order_items`, `payment_transactions`).
2. **Primary Keys**: Explicit `id UUID` or `BIGINT` with Primary Key icon (`isPk: true`).
3. **Foreign Keys**: Explicit `<referenced_table>_id` with Foreign Key icon (`isFk: true`).
4. **Data Types**: Modern SQL types:
   - `UUID` (Identifiers)
   - `VARCHAR(255)` / `TEXT` (Strings)
   - `INTEGER` / `BIGINT` / `DECIMAL(10,2)` (Numbers & Currency)
   - `TIMESTAMP WITH TIME ZONE` (Audit dates: `created_at`, `updated_at`)
   - `BOOLEAN` (Flags: `is_active`, `email_verified`)
   - `JSONB` (Semi-structured metadata)
5. **Relationship Cardinalities**:
   - `1:N`: One-to-Many (e.g., `users` -> `orders`)
   - `1:1`: One-to-One (e.g., `users` -> `user_profiles`)
   - `N:M`: Many-to-Many (modeled via intermediate junction table, e.g., `orders` -> `order_items` -> `products`)

## 6. Color Psychology & Semantic Color Palettes

Nodes are semantically categorized into visual palettes:
- **Indigo / Blue**: Clients, End Users, Frontend Applications, UI entrypoints.
- **Emerald / Green**: Application Backends, Microservices, Workflow Tasks, Compute engines.
- **Amber / Orange**: Databases, Caches, Object Stores, Persistent Data.
- **Rose / Red / Coral**: Gateways, Routers, Firewalls, External Third-Party APIs, Security.
- **Violet / Purple**: Message Queues, Kafka Topics, Event Brokers, AI Agents.
